## The idea

<figure>
  <img src="/img/projects/skryensya-ui-anatomia-accordion-en.png" alt="Accordion anatomy: seven numbered parts over the specimen, with their class names." loading="lazy" />
  <figcaption>Accordion anatomy — every part has a name and a class</figcaption>
</figure>

Skryensya/ui is a contract-first design system: every component starts from a definition, its contract, rather than from CSS and JavaScript wrapped in an API. The contract says what parts the component has, what options it accepts, what attributes it writes, what accessibility rules it must meet and which combinations make sense.

<figure>
  <img src="/img/projects/skryensya-ui-anatomia-comment-thread-en.png" alt="CommentThread anatomy: nine numbered parts over a comment with a reply, with their class names." loading="lazy" />
  <figcaption>CommentThread anatomy — from the avatar to the replies</figcaption>
</figure>

In institutional systems, the usual way to tame the chaos is a single stack for every vendor. It makes sense: it reduces variation and keeps a common line. But it forces teams that don't always start from the same place to make the same technical decision, narrows the pool of possible vendors and raises the cost for the institution. I wanted to resolve that tension differently: allow React, Vue or Vanilla without ending up with three parallel implementations.

The idea comes from what I learned creating and maintaining design systems in production: the <a href="/en/projects/kit-digital-uc" class="editorial-link">Kit Digital UC</a>, the Portal UC and a recent institutional project I still can't show. <a href="https://zagjs.com" class="editorial-link" target="_blank" rel="noopener noreferrer">Zag.js</a> was the technical way in: separating behavior from presentation, using state machines and letting each runtime render the same logic without reinventing it.

## What's interesting

<figure>
  <img src="/img/projects/skryensya-ui-componentes-en.png" alt="“Explore components” page with the catalog grouped by task." loading="lazy" />
  <figcaption>The catalog, organized by the task each piece solves</figcaption>
</figure>

At <a href="https://ui.skryensya.dev" class="editorial-link" target="_blank" rel="noopener noreferrer">ui.skryensya.dev</a> there are more than a hundred documented components. Each page has its contract, its options, the accessibility notes and rendered examples. There are two implementations, React and Vanilla, that come from the same definition and have to produce the same result.

<figure>
  <img src="/img/projects/skryensya-ui-anatomia-button-en.png" alt="Button anatomy: five numbered parts over the specimen." loading="lazy" />
  <figcaption>Button anatomy — the box and its slots</figcaption>
</figure>

I decided accessibility would be part of the contract from day one. Each component declares what accessible name it needs, what states it announces and what minimum size its touch target has, so those rules don't depend on every team remembering them. Several are covered by tests: the contrast of every variant and tone is measured at 4.5:1 in light and dark mode, and motion respects the reduced-motion preference. With a system used by teams this different, I didn't want to depend on anyone's memory.

<figure>
  <img src="/img/projects/skryensya-ui-button-do-dont-en.png" alt="Do/Don't pair for Button: one primary action per region." loading="lazy" />
  <figcaption>Button — one primary action per region</figcaption>
</figure>

The catalog can also be queried as structure through an MCP server. From there you can ask which components exist, how they compose, which combinations are valid and what markup they should produce. The validations compare usage trees across bindings and turn "this should be consistent" into evidence.

## Current state

  <img src="/img/projects/skryensya-ui-tag-do-dont-en.png" alt="Do/Don't pair for Tag: it's acted upon." loading="lazy" />
  <figcaption>Tag — if it can be removed, it's a Tag; if it's only read, it's a Badge</figcaption>

It's a big, deliberately ambitious WIP, but it already has a base that works: Core as the source of truth, public documentation, React and Vanilla implementations, and gates that check consistency. Next is using that same structure for things that are usually built separately: a Figma plugin, a visual editor and an MCP that validates interfaces programmatically.
