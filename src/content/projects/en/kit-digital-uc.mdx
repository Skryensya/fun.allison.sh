## Context

The Kit Digital UC was my first experience with a design system in production. When I joined in 2022 it was already a consolidated base: a component library used across more than 100 of the university's sites, which had standardized interfaces and sped up development.

It's a reference among institutional design systems in Chile. It solves a concrete problem: keeping visual and technical coherence at scale, in an organization with many teams and misaligned development cycles. Later systems have taken lessons from this model, directly or indirectly.

## The problem

That adoption meant any problem stopped being local. The system wasn't badly designed, but it had grown faster than its quality criteria. Accessibility failures lived in base components used everywhere, so they were replicated across the whole system. A single bundle forced loading unnecessary code even on simple sites, and some implementation patterns made it impossible to evolve without side effects.

And there was a critical constraint: the Kit was distributed over a CDN. That favored adoption and centralized updates, but the people consuming it didn't control the version. Every change went straight to production, without us knowing in what context it was used. A tweak to a base component could break navigation, styles or interaction on sites we couldn't audit beforehand.

There was no room for rewrites or coordinated migrations. Improving the system meant working on something alive, where breaking compatibility wasn't an option.

## What we changed

The strategy was incremental: every change had to integrate without friction, coexist with existing implementations and solve real problems without creating new ones.

On accessibility, we fixed decisions that affected the semantics of widely used components. For example, we replaced `background-image` with `<img>` plus `alt`, which gave visibility back to screen readers and search engines. We also normalized interaction patterns and removed incorrect uses of buttons and links, which improved keyboard navigation.

On performance, we moved from a single bundle to modular loading driven by the DOM: a loader inspects the page at runtime and loads only the components it needs. That adds requests but reduces the initial weight. On average, load times dropped ~500 ms.

## How we did it without breaking anything

Given the risk, we validated every change against real Kit implementations and reviewed representative scenarios before integrating it. Decisions followed simple rules: backward compatibility by default, small cumulative changes, and no solution that depended on context.

## My role

My role moved from implementation toward system decisions. I took part in defining the accessibility criteria, the modularization strategy and the impact assessment of each change. The focus stopped being about solving isolated problems and became introducing improvements without compromising stability, in an environment where we don't control how what we build is used.

## Result and learning

Today the system is more consistent, more accessible and lighter. It went from loading everything by default to loading only what's needed, and from inconsistent patterns to more predictable behavior. It supports more than 100 sites and exceeds 2.1 million monthly visits.

The most important thing I learned was going back to basics. Working on the Kit forced me to understand HTML, CSS and JavaScript as a system: real semantics for accessibility and code loading for performance. It was also the first time I built a library consumed in many contexts, and that's where I understood CJS vs ESM in practice, the role of bundlers and how those decisions affect what runs in production.

A library is not just components: it's stable contracts and decisions that have to work in contexts you don't control. In a shared system, quality is measured by how much it can evolve without breaking.
